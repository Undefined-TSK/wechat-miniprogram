## 1. 交付了什么

让用户能在手机上**从打开小程序到答完一关看到成绩、再去错题本重做**，全程不需要后端。

| 页面 | 路径 | 说明 |
|---|---|---|
| 章节地图（首页） | `pages/index` | 概览卡 + 科目条 + 关卡路径 + 星级 + 解锁 + 「从这里继续」 |
| 答题页 | `pages/level` | 答题（原有）+ **结果页增强** + 错题重做入口 |
| 错题本 | `pages/wrong` | **按知识点聚合**、可展开看题面与解析、单组/全部重做 |
| 我的 | `pages/profile` | 成绩单总览 + 分科进度 + 主题切换 + 重置进度 |

支撑层：

| 模块 | 路径 | 说明 |
|---|---|---|
| 学习进度 | `services/progress.ts` | 本地持久化 + 纯函数（星级合并 / 错题本 / 解锁 / 掌握度） |
| 取题服务 | `services/question.ts` | 新增 `fetchQuestionsByIds()`（错题重做合成虚拟复习关） |
| 状态管理 | `store/index.ts` | 新增 `setTheme` / `restoreTheme` / `hasUserTheme`（主题偏好落盘） |

## 2. 数据契约（与云数据库对齐）

```ts
LevelProgress {
  levelId, chapterId, subject,
  bestStars,        // 0-3，只增不减
  bestScoreRate,    // 0-1，只增不减
  bestCostMs,       // 同星级下更快的那次
  attempts, xp,
  lastPlayedAt, firstClearedAt
}

WrongEntry {
  questionId, chapterId, kpIds, type,
  wrongCount,       // 答错次数
  correctStreak,    // 连续答对次数，达阈值 → mastered
  firstWrongAt, lastWrongAt, lastScore,
  mastered          // 标记而非删除：保留「曾经错过」这个事实
}

KpStat { kpId, answered, correct }

ProgressSnapshot {
  version, subject,
  levels, wrongBook, kpStats,
  totalXp, updatedAt
}
```

**为什么数据结构按 collection 形状设计**：将来接云开发时**只换 `ProgressIO` 实现**
（`read`/`write`/`remove` 三个方法），上层页面与业务逻辑一行不改。这是「入口留好」的具体做法。

## 3. 关键设计决策

### 3.1 进度层是纯逻辑，能在 Node 里跑测试

`services/progress.ts` **不 import 题库 / 页面 / 组件**，所有 `wx.*` 调用收在 `ProgressIO` 里。
自检有结构性断言卡住这条（`progress.ts 不依赖题库`）。

如果让进度层自己去查题库拿题目详情，纯函数就变成「依赖数据源的函数」，测试没法造数据。
所以**由页面**（已持有题目列表）通过 `wrongDetails` 把详情传下去。

### 3.2 写失败必须让用户看见

- `ProgressIO.write` 失败**抛错**（不静默吞）
- 页面捕获后设 `saveFailed`，结果页顶部显示醒目提示条
- **但不阻断答题流程** —— 用户刚做完一关，不能因为写盘失败就整页报错

静默丢进度是最让用户恼火的问题：他做完一关发现首页星级没变，会以为程序坏了。

### 3.3 先落盘，再渲染结果页

顺序反了的话，用户快速返回首页会看到旧星级（要再进来一次才对）。
自检用结构性断言卡住：`progressStore.record` 必须在 `setData({finished:true})` 之前。

### 3.4 错题重做 = 虚拟复习局，不写关卡记录

错题本点「重做」→ `?ids=a,b,c` → `fetchQuestionsByIds()` 合成一个 `mode:'review'`
的关卡（id 固定为 `virtual_review`）。

**必须传 `countsAsLevel: false`**，否则两个坏结果：

1. **个人页「已通关 X/3 关」凭空多一关** —— 虚拟关卡不在 `LEVELS` 里，但会写进 `levels`
2. **几组不相干的错题互相覆盖 `attempts`/`xp`** —— 它们共用一个虚拟 id

传 `false` 后：**只更新错题本与知识点统计，不写关卡记录**，但经验照算（重做本身有价值，应鼓励）。

虚拟复习关的星级阈值放宽到 `[0.5, 0.8, 1.0]`（重做的题都是曾经错过的，
门槛与首次学习一致会让人反复卡在同一关，反而打击信心）。

### 3.5 主题：用户手动选择优先于系统

- 主题偏好与进度快照**用两个存储键**（`xxgk:theme:v1` / `xxgk:progress:v1`）
  —— 否则「重置进度」会顺手清掉用户的深色模式设置
- 启动顺序：先 `restoreTheme()`，再跟随系统
  —— 反了会「我选了深色，重进又变浅色」
- 系统主题变化时用 `hasUserTheme()` 判断是否跳过

## 4. 自检覆盖（三处）

### 4.1 引擎纯函数（`tests/engine.test.mjs` 第 10 节，69 项）

星级只增不减 / XP 累加 / 错题进本与移出 / 掌握后又答错 / 知识点统计 /
解锁判定 / 章节完成度 / 脏数据降级 / 落盘往返 / `countsAsLevel` 语义。

### 4.2 接线自检（`tests/wiring.test.mjs` 第 7 节，32 项）

- 页面注册 + **所有 `navigateTo` 目标逐条校验**（漏注册真机点击无反应）
- 进度层不依赖题库 / 主题键与进度键分离
- 落盘顺序断言 / 保存失败有可见提示 / 掌握阈值来自配置
- 重置进度有二次确认
- **页面样式覆盖完整性**：扫 wxml 的 class 是否都有定义

### 4.3 页面逻辑自检（`tests/pages.test.mjs`，81 项）

打桩 `wx` / `Page` / `getApp`，把页面 import 进来，真跑 `onLoad`/`onShow`/交互方法，
用简易 `setData` 收集渲染数据。

**补的是前三套的真实盲区**：小程序 TS 由微信开发者工具编译，Node 侧不类型检查也不跑页面。
于是「引用不存在的实例字段」「**setData key 路径写错**」（模板永远拿不到值且不报错）
「派生数据混进 NaN」「跳转 url 拼错」这些本机全测不出来，只在真机暴露。

**两个必踩的坑（已写进文件注释）**：

1. **必须 `process.exit()`** —— 答题页用 `setInterval` 走计时（小程序里对），
   在 Node 里是不会自己结束的活跃句柄 → 进程跑完不退出，看起来像「卡死」
2. **造答案不能直接用 `localJudgeKey.key`** —— 它在 `exact`/`set` 下与作答形态同构，
   但 `normalize`（填空）是 `{mode, accepted}`、`output`（程序输出）是 `{expected}`，
   直接当答案会被判错 → 让「答对后错题应移出」这类断言假失败。要按策略逐类展开。

## 5. 界面口径

- **单屏只做一个决策**：首页只回答「我现在该打哪一关」，不放仪表盘
- 关卡路径：已通关实心圆点 + ✓ + 星级；未解锁虚线圆点 + 灰卡 + 条件说明；
  「推荐下一关」主色描边 + 「从这里继续」
- 错题本**按知识点聚合**，不是时间流水账 —— 用户需要知道「我哪块弱」，不是「我周三错了三道题」
- 我的页有「**还在路上**」灰卡，诚实列出未做的功能（账号同步 / 排行榜 / 编程题评测 / AI 出题），
  并说明「当前进度保存在本机，换手机会丢失」

## 6. 已知边界（本轮不做）

| 项 | 说明 |
|---|---|
| 多设备同步 | 进度只在本机。接云开发时换 `ProgressIO` 实现即可 |
| 艾宾浩斯复习调度 | 错题本现在是「连对 2 次移出」的极简规则，完整调度留到 Phase 5 |
| 掌握度算法 | `KpStat` 只统计对错次数，完整算法（λ/α/β）留到 Phase 5 按配置表实现 |
| 分科目 | 只有 C 语言有题库；其余 4 科在首页显示「题库补充中，敬请期待」 |
