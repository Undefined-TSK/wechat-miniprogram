## 0. 已锁定的关键决策（v1.0 结论，不再改）

| 决策项 | 结论 | 理由 |
|---|---|---|
| 小程序端技术栈 | **微信原生 + TypeScript** | 性能上限最高、微信能力兼容性最好、审核坑最少 |
| 后端架构 | **混合架构**：业务走微信云开发，判题 + AI 走自建服务 | 云函数无法运行 Docker，编程题判题必须独立沙箱服务 |
| 题库来源 | **自建题库 + AI 辅助生产 + 人工审核** | 版权可控、可做知识点打标与难度标定 |
| 首发范围 | **C语言单科完整闭环**，题型引擎数据驱动 | 用最小成本验证留存与付费意愿，扩科零改代码 |

### 📌 我的假设（如与实际不符请指出）

1. 只做微信小程序，不考虑多端 → 所以选原生而非 uni-app。
2. 团队规模 2-4 人（1 前端 + 1 后端 + 1 教研/运营），周期按 16 周排（v1.1 因新增内容生产与运营环节延长 2 周）。
3. 首批不追求 UGC 题目投稿，题目全部来自自建题库。
4. 有已认证的微信小程序主体（企业/个体工商户）。
5. 首批不接入微信支付实物交易，会员/虚拟币的 iOS 端问题需在 Phase 0 确认。

### ⚠️ 三条必须提前确认的红线

| 红线 | 为什么是红线 | 处理方式 |
|---|---|---|
| **教育类目资质** | 「教育 > 在线教育」通常要求《办学许可证》或与持证机构合作，**最容易卡死项目且周期不可控** | Phase 0 第一件事：公众平台后台试选类目看实际要求。备选：持证机构合作 / 调整产品定位与类目 |
| **题库内容版权** | 直接复制教材习题、历年真题属高侵权风险，被投诉即下架 | 每道题带 `source` 台账；改编题注明「改编」；AI 生成题必须人工审核入库 |
| **iOS 虚拟商品支付** | 苹果政策禁止 iOS 端用微信支付购买虚拟商品，违反即拒审 | iOS 端隐藏支付入口。⚠️ 需核实最新政策 |

## 1. 产品结构

### 1.1 内容层级模型

```
科目 Subject（C语言 / 英语四级 / 英语六级 / 高等数学 / 线性代数 / …）
└── 章节 Chapter（如 C语言 → 变量与数据类型）
    └── 知识点 KnowledgePoint（如 → 整型与浮点型、类型转换）
        └── 关卡 Level（如 → 类型转换·入门）
```

**关卡四种形态**

| 形态 | 题目构成 | 星级规则 | 解锁条件 |
|---|---|---|---|
| 普通关 | 单一知识点，5-8 题 | 正确率 60%/80%/100% → 1/2/3 星 | 前一关 ≥1 星 |
| Boss 关 | 章节混合题型，10-15 题，限时 | 正确率 + 剩余时间 + 最高 Combo 综合 | 本章累计星数达阈值 |
| 挑战关 | 高难题，含编程题，进排行榜 | 只记分数不记星 | 章节通关后开放 |
| 自适应重练关 | 系统按错题 + 掌握度动态生成（算法见 §5） | 不记星，只清错题 | 有错题即开放 |

### 1.3 分包规划

| 包 | 内容 | 说明 |
|---|---|---|
| **主包** | tabBar 4 页 + 登录/隐私弹窗 + 答题引擎组件 + 通用组件 + 主题样式 | 答题引擎是最高频路径，必须留主包；**内控 1.5MB 以内** |
| pkg-subject | 科目广场、章节地图、关卡预习、结算页 | 预下载 |
| pkg-tools | 错题本、模拟考试、学习报告、学习计划、AI 对话 | |
| pkg-social | PK、组队副本、排行榜、学习搭子、成果卡片 | |
| pkg-shop | 会员、积分商城、抽卡、宠物、邀请 | |
| pkg-admin | **仅做审核与紧急修题**：题目通过/驳回、题目下线、紧急修答案三个动作 | 独立分包；不做完整 CRUD（完整录题在 Web 管理端，见 §8.7） |

**体积控制规则（v1.1 收紧）**

1. 主包体积上限**内控 1.5MB**，不等到 2MB 才动手。
2. **题型渲染器若单包体积超 300KB，一律走「分包异步化」按需加载**（`require.async` / `componentPlaceholder`），绝不塞进主包。按题型分片：`renderers/choice`、`renderers/code`、`renderers/audio`、`renderers/matrix`。
3. 题图、LaTeX SVG、听力音频全部走云存储 + CDN 长缓存，不进包。
4. **总包上限不预设数值，以提审时微信官方文档为准**（平台调整过多次，写死数字只会误导排期）。

## 3. 通用题型引擎（核心资产）

### 3.1 设计原则

题目是**纯数据**，页面不感知题型：

```javascript
{
  _id: "q_xxx",
  subject: "c_lang",
  chapterId: "ch_01",
  kpIds: ["kp_int_float", "kp_type_cast"],   // 可挂多个知识点，用于掌握度计算
  type: "single_choice",                      // 决定用哪个渲染器/判分器
  difficulty: 2,                              // 1-5，用于自适应与组卷
  payload: { /* 题型私有数据：题干、选项、代码、音频URL、空槽位… */ },
  answer: { /* 标准答案 */ },
  judge: {
    strategy: "exact",   // exact|set|normalize|numeric|output|sandbox|ai
    options: { tolerance: 1e-6, ignoreCase: true, trimAll: true, partialCredit: 0 }
  },
  analysis: { text: "...", latex: ["\\int_0^1 x^2 dx"], aigc: false },
  source: { type: "original", note: "自编", license: "self" },  // 版权台账
  stats: { attempts: 0, correctRate: 0, avgCostMs: 0, discrimination: 0 },
  status: "published"                         // draft | reviewing | published | offline
}
```

**新增题型 = 注册一个渲染器 + 注册一个判分器**，不改任何页面代码。

### 3.2 判分策略分三层

| 层 | 策略 | 适用 | 实现位置 |
|---|---|---|---|
| L1 确定性 | `exact` / `set`（多选，支持半对半分）/ `normalize`（去空格、忽略大小写、全半角归一、正则、多答案任一）/ `numeric`（数值容差）/ `output`（逐行比对，忽略行尾空白） | 单选、多选、填空、判断、程序填空、程序阅读输出 | 客户端 + 云端（**需防作弊的场次放云端**） |
| L2 编译判分 | `sandbox`：编译 → 跑测试用例 → 按测试点/subtask 给分（安全要求见 §8.4） | 基础编程、综合编程、算法实现 | 自建 Docker 判题服务 |
| L3 AI 语义判分 | `ai`：评分维度 + 满分点 → 结构化评分；**与关键词双通道交叉验证，阈值见 §6** | 名词解释与简答、翻译、作文、证明题、复杂度分析 | AI 网关 |

### 3.3 C语言题型矩阵（10 种）

| 编号 | 题型 | 判分策略 | 交互组件 | 优先级 |
|---|---|---|---|---|
| T1 | 单项选择 | exact | 选项卡片（点选即判） | P0 |
| T2 | 多项选择 | set（支持半对半分） | 选项多选 + 提交 | P0 |
| T3 | 填空 | normalize / numeric | 单行输入框（可多空） | P0 |
| T4 | 判断 | exact（布尔） | 双按钮 | P0 |
| T5 | 名词解释与简答 | **ai** + 关键词命中 | 多行文本 | P1 |
| T6 | 程序填空 | normalize + 可选编译校验 | 代码填空槽 | P0 |
| T7 | 程序阅读与输出 | output | 多行文本 / 终端输出框 | P0 |
| T8 | 基础编程 | **sandbox** | WebView 代码编辑器（C） | P1 |
| T9 | 综合编程 | **sandbox**（多测试点 subtask 给分） | 多文件编辑器 | P1 |
| T10 | 算法与复杂度 | 混合：选择/填空 + sandbox + **ai** | 组合题容器 | P2 |

### 3.4 其他科目题型配置（数据驱动，无需改引擎）

| 科目 | 题型清单 |
|---|---|
| 英语四级/六级 | 听力选择（音频）、听力填空、词汇单选、选词填空、完形填空、阅读理解、长篇匹配、翻译（AI 批改）、写作（AI 批改） |
| 高等数学 | 单选、多选、填空（LaTeX 输入）、判断、计算题（步骤给分）、证明题（AI 批改） |
| 线性代数 | 单选、多选、填空、判断、矩阵运算题（矩阵输入组件）、计算题、证明题 |

### 3.5 答题状态机

```
IDLE → LOADING(取题) → ANSWERING(计时/Combo计数)
  → SUBMITTING(本地即时判分 或 上报云端)
  → FEEDBACK(对/错反馈动效 + 解析)
  → NEXT(下一题) 或 FINISH(无题了 → 结算)
异常分支：NETWORK_ERROR(重试/离线队列) / TIMEOUT / CHEAT_DETECTED(中止并上报)
```

约束：**setData 只传变化字段**；计时/Combo/索引放非渲染数据区；作答记录先落本地队列，联网后批量上报。

## 4. 玩法系统设计

| 玩法 | 机制 | 设计要点 |
|---|---|---|
| **连胜 Streak** | 每日完成 ≥1 关卡保连胜；连胜天数给经验加成（1.0x → 1.5x） | 断连用「补签卡」挽回（广告/积分），降低流失 |
| **段位 Rank** | 青铜→白银→黄金→铂金→钻石→星耀→王者；按科目 XP；赛季 8 周 | 升段/掉段有明确阈值；设「保护位」降低挫败 |
| **Combo** | 连对递增倍率（×1 → ×1.2 → ×1.5 → ×2），答错归零 | 影响关卡评分与掉落；Boss 关 Combo 计入星级 |
| **1V1 PK** | 同知识点同难度抽题 → 同题竞速 5 题 | **服务端出题与判分**；ELO 匹配；异常时长判定可疑 |
| **学习搭子** | 1V1 同桌；共享每日任务与连胜 | 匹配规则见下 |
| **组队副本** | 3-5 人 Boss 关；正确率转伤害；限时 10 分钟 | 掉落平分 + 贡献榜；**AI 队友规则见下** |
| **排行榜** | 好友/科目/全站；日/周/赛季 | 服务端计算；**反作弊见 §10.3** |
| **成果卡片** | 结算/周报生成分享图（Canvas + 小程序码） | **分享不设奖励**（合规） |
| **抽卡** | 宠物皮肤、称号、表情、复活卡、经验卡 | **概率公示 + 保底 + 未成年人限额** |
| **电子宠物** | 答题喂养 → 饱食度/心情/经验 → 进化 → 被动加成 | 情感陪伴是留存钩子；宠物会「催你学习」 |

### 4.1 学习搭子匹配与解绑规则（v1.1 新增）

**匹配维度（依次过滤）**

| 顺序 | 维度 | 规则 |
|---|---|---|
| 1 | 科目 | 必须相同（搭子关系绑定在某一科目上） |
| 2 | 活跃时段 | 近 7 日日均活跃时段重叠 ≥ 2 小时 |
| 3 | 进度相似度 | 章节进度差 ≤ 1 章；知识点掌握度向量余弦相似度 > 0.6 |

**匹配流程**

```
系统按上述三维度打分排序 → 推荐 3 个候选（展示「同科 · 同时段 · 进度接近」标签）
→ 任一方发起邀请（订阅消息通知） → 对方接受即绑定
→ 同时仅允许 1 个搭子；邀请 48 小时未响应自动失效
```

**解绑规则**

| 场景 | 处理 |
|---|---|
| 主动解除 | 任一方可解除，双方均收通知；**7 天冷却期**内不可再次绑定新搭子（防刷奖励） |
| 双方 7 天均无学习行为 | 系统自动解绑并推送提示 |
| 一方 14 天不活跃 | 自动解绑，另一方可立即重新匹配 |
| 被举报骚扰 | 人工审核后强制解绑，并限制邀请权限 |

**搭子权益**：共同连胜天数、对方每日任务进度可见、每日可发送 1 次提醒（订阅消息）。
**合规**：提醒走订阅消息模板（用户主动订阅），不做强制打扰；搭子关系不产生任何分享奖励。

### 4.2 组队副本 AI 队友规则（v1.1 新增）

- AI 队友**必须显式标识**（昵称前缀「机器人小助手」+ 头像角标），不得伪装真人。
- AI 队友**不计入贡献榜**，不参与掉落平分。
- AI 队友不产出稀有物品，避免用户认为「AI 抢了奖励」而伤信任。
- AI 队友只在队伍人数不足且等待超 30 秒时补位，真人加入后自动退出。

## 5. 学习算法设计（v1.1 新增）

### 5.1 知识点掌握度

```
mastery(kp) = Σ(w_i × c_i) / Σ(w_i)          i ∈ 最近 N 次作答（滑动窗口 N = 20）

c_i = 1（答对）或 0（答错）；部分给分题型取得分率（0~1）
w_i = e^(-λ × Δt_i) × (1 + α × (d_i - 3) / 2) × (答错 ? β : 1)

λ = 0.05 /天    时间衰减（越久远的作答权重越低）
α = 0.3         难度权重系数（d_i 为题目难度 1-5）
β = 1.2         答错惩罚系数（答错比答对更值得记住）
```

**掌握度分档**

| 区间 | 状态 | 系统行为 |
|---|---|---|
| < 0.4 | 未掌握 | 优先推送基础题；出现在每日任务 |
| 0.4 - 0.7 | 待巩固 | 混合难度；错题重练主要来源 |
| 0.7 - 0.9 | 已掌握 | 提单题难度；降低推送频率 |
| > 0.9 | 精通 | 只做周期性复习与挑战题 |

### 5.2 自适应难度选择

**目标难度映射**

```
mastery < 0.4        → target_d = 1 ~ 2
0.4 ≤ mastery < 0.7  → target_d = 2 ~ 3
0.7 ≤ mastery < 0.9  → target_d = 3 ~ 4
mastery ≥ 0.9        → target_d = 4 ~ 5
```

**实时微调（同一关内）**：连对 2 题 → 难度 +1 档；连错 2 题 → 难度 −1 档（clamp 到 1~5）。
**组卷约束**：自适应重练关 = 错题（优先）+ 掌握度最低 2 个知识点各抽 3 题；难度分布 60% 目标档 + 20% 低一档（建立信心）+ 20% 高一档（拉伸）。

### 5.3 艾宾浩斯复习调度

```
复习间隔序列（天）：1 → 2 → 4 → 7 → 15 → 30
nextReviewAt = lastReviewAt + interval[stage]

复习通过 → stage +1（进入下一间隔）
复习失败 → stage 归 0，掌握度按 §5.1 重新计算（时间衰减后权重下降）
连续 3 次通过且掌握度 > 0.9 → 移出错题本（标记 mastered）
```

**每日错题本推荐** = 今日到期题（`nextReviewAt ≤ today`）+ 掌握度最低 2 个知识点各抽 3 题。

> ⚠️ **实现纪律**：λ、α、β、N、间隔序列**全部放云端配置表**，不硬编码。上线后用真实数据校准——参数写死在代码里等于放弃调优能力。

## 6. AI 能力设计

| 能力 | 触发 | 实现要点 |
|---|---|---|
| 题目解析 | 答题后展开 | 先查题库预置 `analysis`；缺失则 AI 生成 → 人工审核入库缓存，避免重复计费 |
| 主观题批改 | 简答/名词解释/翻译/作文提交 | 评分维度 + 满分点 → 结构化 JSON；**与关键词双通道交叉验证（阈值见下）** |
| 学习计划生成 | 用户设定目标 | 输入：掌握度 + 剩余天数 + 每日可投入时长 → 输出每日任务序列 |
| 陪伴式提醒 | 每日定时 + 宠物状态 | 订阅消息；文案经内容安全过滤；可关闭 |

### 6.1 AI 批改阈值规则（v1.1 新增）

```
S_ai  = AI 评分（0-100）
S_kw  = 关键词命中分（0-100，按满分点命中率线性折算）
conf  = AI 自报置信度（0-1）

if |S_ai - S_kw| > 20            → 转人工复核 / 给「参考分」并标注
else if conf < 0.7               → 给「参考分」+ 明示「AI 批改，仅供参考」
else                             → 最终分 = 0.6 × S_ai + 0.4 × S_kw（正常计分）
AI 服务不可用                     → 退化为纯关键词分，标注「机器初判，待复核」
```

**配套要求**

1. 所有 AI 批改结果页面必须带可见标识；`conf < 0.7` 的题目额外展示「本题已标记待人工复核」。
2. 用户可对 AI 批改结果发起**申诉**，走后台工单，48 小时内响应。
3. AI 批改日志留存（输入、输出、置信度、最终分），用于后续校准 Prompt 与阈值。

### 8.3 成本模型（v1.1 新增）

> ⚠️ **口径声明**：以下是**量级估算**，用于判断「成本结构」和「迁移时机」，不是报价。所有单价**必须按腾讯云/微信云开发官方最新价目表代入核实**。估算误差按 ±50% 看待。

#### 单活跃用户日用量假设

| 行为 | 日均量 | 说明 |
|---|---|---|
| 答题 | 20 题 | 普通关 1-2 关 + 错题重练 |
| 云函数调用 | 70 次 | 取题 20 + 提交 20 + 进度上报 15 + 其他 15 |
| 云数据库读 / 写 | 60 / 60 次 | 取题关联查询 + 答题记录/进度/任务写入 |
| 题目资源流量 | ≈ 1MB | LaTeX SVG + 题图（无音频时） |
| 编程题判题 | 3 次 | 仅编程关；单次编译+运行 ≈ 2 秒 CPU |
| AI 调用 | 1-3 次 | 解析 2 + 批改 1，**按 70% 缓存命中率折算** |

#### 三档成本估算（人民币 / 月）

| 成本块 | DAU 1,000 | DAU 5,000 | DAU 20,000 | 说明 |
|---|---|---|---|---|
| 云函数调用 + 资源 | ¥40 – 90 | ¥200 – 450 | ¥800 – 1,800 | 210万 / 1050万 / 4200万 次/月 |
| 云数据库读写 | ¥30 – 70 | ¥150 – 350 | ¥600 – 1,400 | 360万 / 1800万 / 7200万 次/月 |
| 云存储 + CDN 流量 | ¥5 – 20 | ¥25 – 100 | ¥100 – 400 | 30 / 150 / 600 GB/月；**接入听力音频后 ×5-8** |
| 判题沙箱实例 | ¥60 – 100 | ¥120 – 200 | ¥180 – 300 | 1 / 2 / 3 台 2C4G 轻量；低峰缩容 |
| AI 调用 | ¥60 – 400 | ¥300 – 2,000 | ¥1,200 – 8,000 | **最大变量**，取决于模型档位与缓存命中率 |
| **合计** | **¥195 – 680** | **¥795 – 3,100** | **¥2,880 – 11,900** | |
| **单用户月成本** | ¥0.20 – 0.68 | ¥0.16 – 0.62 | ¥0.14 – 0.60 | 规模上去后边际成本下降 |

**关键结论**

1. **AI 是唯一会失控的成本项**，区间跨度 6 倍以上。必须：强缓存（同题解析只生成一次）、按题型路由模型（选择/填空走轻量模型，简答/作文走旗舰模型）、设用户级日额度（免费用户每日 AI 调用上限）。
2. **判题是固定成本**，跟 DAU 线性但斜率很缓（每 5,000 DAU 加约 1 台 2C4G）。
3. **云开发是变动成本**，跟 DAU 近线性增长，且单价高于自建数据库。

#### 迁自建触发规则

> **规则：当微信云开发（云函数 + 云数据库 + 云存储）月成本 > 同规格自建（轻量/CVM + MySQL/Redis + 对象存储）月成本 × 1.5 时，把高频读写业务迁到自建服务。**

配套的**可观测触发指标**（任一连续 7 天满足即启动评估）：

| 指标 | 阈值 |
|---|---|
| 云函数调用量 | > 2,000 万次/月 |
| 云数据库读写量 | > 4,000 万次/月 |
| 单集合日读写 | > 200 万次 |
| 云开发月账单 | > ¥1,000 且增速 > DAU 增速 |
| 排行榜/排行榜类查询 P95 延迟 | > 800ms |

**迁移顺序**（先迁最贵的，业务风险由低到高）：

1. 排行榜与统计类聚合（读写最密、可容忍短暂不一致）
2. 学习进度与错题（数据量大、写频繁）
3. 题库读取（读多写少，可加缓存）
4. **不迁**：用户登录态、订阅消息、内容安全、支付回调——这些强绑微信生态，迁了只会更麻烦。

**成本优化优先级**：AI 强缓存（省最多）> 取题合并批量请求（减少云函数调用次数）> 答题记录批量上报 > 资源走 CDN 长缓存 > 实例按峰值缩容。

### 8.4 判题沙箱安全加固（v1.1 新增 · Phase 2 已实现于 judge-service）

> 原 v1.0 的「禁网 + 只读根文件系统 + 限资源」是**底线**，不是全部。以下为防沙箱逃逸的必需项，**不是可选项**。

| # | 加固项 | 配置要点 | 防的是什么 |
|---|---|---|---|
| 1 | **seccomp 白名单** | 只放行编译/运行必需的系统调用；显式禁 `ptrace`、`socket`、`mount`、`unshare`、`clone` 的越权 flag | 系统调用层的容器逃逸 |
| 2 | **非 root 运行** | 独立 UID/GID（如 `nobody`），禁止 setuid/setgid 二进制，`no-new-privileges` | 提权 |
| 3 | **cgroup 隔离** | v2：`cpu.max`、`memory.max`、`memory.swap.max=0`、**`pids.max`（防 fork 炸弹）**、`io.max` | 资源耗尽型攻击 |
| 4 | **编译与运行分容器** | 编译容器：10s 超时 / 512MB / 可写临时目录；产出可执行文件后销毁。运行容器：最小镜像，只跑二进制，1s / 256MB | 用编译期做手脚、编译产物带毒 |
| 5 | **提交代码大小上限** | 单文件 ≤ 64KB，总 ≤ 256KB，超出直接拒绝 | 超大源文件撑爆编译器和磁盘 |
| 6 | **编译超时** | 编译 10s、运行 1s/测试点（可按题型配置），硬杀进程组 | 编译期死循环、模板元编程炸弹 |
| 7 | **禁止 ptrace** | seccomp + `cap_drop ALL` 双保险 | 进程注入与调试逃逸 |
| 8 | 禁用网络 | `network=none` | 外联 C2 / 拉取恶意代码 |
| 9 | 只读根文件系统 + 独立 tmpfs | 根 fs `read-only`，`/tmp` 挂独立 tmpfs 且容器销毁即清 | 持久化后门 |
| 10 | 输出大小上限 | stdout/stderr 各 ≤ 1MB，超出截断并标记 | 输出炸弹撑爆日志与内存 |
| 11 | 提交频率限制 | 单用户 30 次/分钟、300 次/日；超限冷却 | 刷判题资源 |
| 12 | 判题节点网络隔离 | 判题节点单独安全组，只接受来自业务层的鉴权调用 | 判题节点被直接攻击 |

**进阶隔离方案（可选，成本更高）**：`runc + 上述加固` → **`gVisor`**（用户态内核，隔离强度显著更高）→ `Kata Containers`（VM 级隔离）。建议 Phase 2 先用 `runc + 加固`，Phase 5 若对外开放编程题或遭遇攻击再升级 gVisor。

**判题结果分类返回**（便于前端展示与统计）：`AC`（通过）/ `WA`（答案错误）/ `CE`（编译错误，返回编译器原始信息）/ `RE`（运行时错误）/ `TLE`（超时）/ `MLE`（超内存）/ `OLE`（输出超限）/ `SE`（系统错误，需运维介入）。

### 8.5 三个必须提前做 POC 的技术难点

| 难点 | 问题 | 推荐方案 | 备选 |
|---|---|---|---|
| **LaTeX 渲染** | 小程序无 DOM，KaTeX 不能直接跑 | **构建期服务端预渲染为 SVG**，随题目存入题库，客户端只渲染 SVG 字符串 | `towxml` / `mp-html` + LaTeX 适配器；自研节点转换 |
| **代码编辑器** | 原生 `textarea` 无高亮、缩进差 | **WebView 内嵌 CodeMirror 6 / Monaco**，postMessage 通信 | 自研轻量高亮 textarea（体验明显更差，仅降级） |
| **听力音频** | 需后台播放、倍速、续播 | `wx.createInnerAudioContext` + `playbackRate`；`app.json` 声明 `requiredBackgroundModes: ["audio"]`；音频存云存储走 CDN | — |

### 8.7 题库后台（Web 管理端为主）

小程序的录题效率极低，题库后台以 **Web 管理端**（Vue3 + Element Plus，或基于云开发 Web SDK）为主；小程序端 `pkg-admin` **只做三个动作**：审核通过/驳回、题目下线、紧急修答案。

| 模块 | 功能 |
|---|---|

| 维度 | 规范 |

| 认知负荷 | **单屏只呈现一个决策**：答题页仅显示当前题；Boss 关才引入倒计时压力 |
| 反馈节奏 | 答对：即时反馈 + 0.4s 后自动下一题；答错：停留等用户点击「查看解析」 |

### 10.2 防作弊机制

| 场景 | 措施 |
|---|---|
| 通用 | ①答案不下发 ②需防作弊场次服务端判分 ③异常作答时长检测 ④提交频率限制 |
| 答题 | 单题作答 < 0.5s 标记可疑；整关平均时长低于知识点基线 40% 标记可疑 |

### 10.3 排行榜反作弊（v1.1 新增）

排行榜是作弊重灾区，以下三条**必须有**：

**① 异常分数检测（写入即校验）**

```
单日 XP 理论上限 = Σ(各关卡理论最大 XP) × 单日最大可通关次数
   —— 按「最快通关速度 × 关卡数」推算，超过即判定异常

触发后的处理：
  分数线以上 → 该用户当周期成绩不展示（榜单置灰 + 「成绩审核中」），并写入 anti_cheat_flags
  同时校验：单题作答时长下限、答对率是否偏离同题人群 3 个标准差
  连续 2 个周期异常 → 冻结排行榜参与资格
```

**② 封榜前快照**

```
日榜 / 周榜 / 赛季榜在结算前 10 分钟「封榜」：
  · 停止接受新分数写入（写入进入下一周期）
  · 生成 leaderboard_snapshots 快照（frozen: true）
  · 奖励按快照发放，任何后续分数变动不影响已结算榜单
目的：防止最后一秒刷榜，也让奖励发放有不可篡改的依据
```

**③ 申诉入口**

```
榜单页提供「成绩异常申诉」入口 → 生成工单 → 后台人工复核
承诺响应时限 48 小时；申诉期间该用户成绩保持「审核中」状态
申诉成功 → 恢复展位 + 补发奖励；申诉失败 → 展示具体判定依据（不只回「违规」）
```

**处罚分级**：首次 → 警告 + 清除当期分数；二次 → 该周期禁入排行榜；三次 → 禁用排行榜与 PK 功能 30 天。

### 11.2 冷启动运营

**种子用户来源**

| 渠道 | 做法 | 预估贡献 |
|---|---|---|
| 高校社团 | 计算机协会、考研社、学习部合作；社团内测 + 专属邀请码 | 首批 200-400 人 |
| 班级群 | 通过校园大使进入班级群；提供班级排行榜玩法 | 规模最大，转化依赖大使质量 |
| B站/小红书/知乎学习博主 | 内容植入（如「C语言期末突击」视频挂小程序）+ 专属邀请码分销 | 声量与转化兼顾 |
| 校园大使 | 每校 1-2 人，按「拉新 + 留存」双指标给积分/会员奖励 | 长期滚动 |
| 考试节点 | 四六级报名后、期末前 4 周集中投放 | 天然流量高峰 |

**首月目标（可量化）**

| 指标 | 目标 | 说明 |
|---|---|---|
| DAU | **500** | 主目标 |
| 次日留存 | **≥ 30%** | 验证核心闭环是否成立 |
| 7 日留存 | ≥ 15% | 验证连胜/段位是否起作用 |
| 人均日答题 | ≥ 15 题 | 低于 10 题说明关卡节奏有问题 |
| 首日完成 3 关比例 | ≥ 40% | 验证新手引导质量 |

**增长钩子**

1. **免费会员 7 天**（新用户注册即得，不打分享门槛）——让用户体验完整权益，为 Phase 5 付费转化铺垫。
2. **邀请有礼**：邀请双方各得积分/道具；**奖励绑定「好友完成首次闯关」而非「分享行为」**（合规要求）。
3. **班级/社团排行榜**：让同辈竞争自然发生，是主打传播点，比分享卡片更有效。
4. **连胜补签卡**：断连可挽回，降低「一天没学就再也不来了」的流失。

**上线节奏**

```
T-7  预热：博主内容投放 + 社团内测招募
T0   上线：社团群首发 + 校园大使同步 + B站/小红书内容挂载
T+7  首次迭代：按真实数据调关卡难度曲线与题量（第 1 章通过率 < 50% 则降难度）
T+14 首个活动：闯关赛 / 排行榜冲刺（含实物或会员奖励）
T+28 复盘：留存与付费意愿评估 → 决定是否启动 Phase 4 后半段（宠物/抽卡）
```

**风险提示**：上线前必须完成 C语言**全部 8 章**内容，否则会出现「玩到第 3 章没内容」的致命体验断裂——这是内容型产品最常见的冷启动死法。
