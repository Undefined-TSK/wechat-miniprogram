## 1. 为什么先做「工具链」再做内容

题库是**纯数据**。数据错了不会编译报错，只会在用户答题那一刻表现成怪现象：

| 录题错误 | 用户看到的现象 | 排查难度 |
|---|---|---|
| 选择题答案填了个不存在的选项 key | 怎么选都判错，且没有任何报错 | 极高 —— 没有任何日志指向题库 |
| 填空题有 3 个空、答案只给了 2 组 | 第 3 空永远是错的 | 高 —— 看起来像判分器 bug |
| 关卡引用了不存在的题目 id | 点进关卡直接白屏 | 中 |
| 缺 `source` 版权台账 | 提审时被逐题驳回 | 低（但返工成本高） |
| 解析为空 | 错题本点开是空白，用户以为功能坏了 | 中 |
| 同一道题横跨练习关与 Boss 关 | Boss 关里答对也判 0 分 | **极高** —— 练习关里完全正常 |

手写 51 道题的数据、每道都靠肉眼检查，出错是必然的。所以顺序是：
**先建闸门，再灌内容**。

## 2. 新增：题库校验器（录题闸门）

### 2.1 文件

| 文件 | 角色 |
|---|---|
| `miniprogram/mock/bank-validator.ts` | **校验逻辑本体**（纯函数，可复用） |
| `scripts/check-bank.mjs` | 录题工具：`npm run bank:stats` 看统计、`npm run bank:check` 体检 |
| `tests/wiring.test.mjs` 第 6 节 | CI 闸门：提交时自动跑，有一条不合规就红 |

三者**共用同一份校验逻辑**，所以不会出现「工具说没问题、CI 说有问题」的漂移。

### 2.2 校验规则清单

**引用完整性**
- 章节 → 科目；知识点 → 章节；题目 → 科目/章节/知识点；关卡 → 章节/题目
- 题目 id、关卡 id 唯一性

**逐题必填**
- `id` / `subject` / `chapterId` / `type` / `difficulty`(1-5) / `analysis.text` 非空 / `source.type` + `source.license`

**题型 ↔ 判分策略匹配**（与引擎注册表一致）

| 题型 | 允许的策略 |
|---|---|
| single-choice | exact |
| multi-choice | set |
| fill-blank | normalize |
| program-output | output |
| code-editor | sandbox |

**按题型校验 payload 与答案形态**
- 选择题：选项 ≥ 2、key 唯一非空、文本非空；**答案必须能在选项里找到**；多选至少 2 个正确项
- 填空题：`blanks` 非空、key 唯一；**multi 模式下空位数必须等于 `accepted` 组数**（高发错误）
- 程序输出题：`answer.expected` 非空、必须有 `payload.code.content`
- 编程题：必须带 `{ kind: 'testcases', planRef }`、必须声明 `language`

**关卡**
- 题目列表非空（空关卡点进去立刻结束）
- `starThresholds` 必须是 3 个值、递增、落在 (0,1]
- Boss 关必须有 `timeLimitMs`

**跨关卡互斥（真踩过的坑）**
- 同一道题不得同时出现在「本地判分关（practice/review）」与「服务端判分关（boss/challenge）」

### 2.3 校验器自己也被验证过

写校验器最大的风险是「它什么都没查出来，但我以为它查了」。
所以用 **12 个故意写错的用例**逐条验证它确实能抓到每一类错误（全部 ✓ 命中）。

## 5. 关键决策：Boss 关为什么需要「专属题」

### 5.1 问题的发现

把题库从 3 关扩到 11 关时，我给校验器加了一条「练习关与 Boss 关题目不得重叠」的规则。
加完立刻**在自己刚写的关卡数据上报错**：Boss 关的 6 道题全部来自练习关。

### 5.2 为什么这是真 bug（不是误报）

Boss 关（`mode: 'boss'`）**不下发 `localJudgeKey`** —— 这是设计约定，
Boss / PK / 排行榜都必须服务端判分。

但服务端目前只有**一条**判分入口：编程题的 `sandbox`。
选择题、填空题、程序输出题的「判分依据」就是 `localJudgeKey` 本身，服务端没有对应的比对入口。

于是「练习关的选择题搬进 Boss 关」的组合必然走向这个分支：

```ts
// miniprogram/services/judge.ts
// ③ 落到这里说明题目配置有问题：非练习关的选择/填空类题没有 localJudgeKey
return { correct: false, score: 0, layer: 'remote',
  detail: '题目配置异常：该题型…在非练习关必须下发判分依据…请反馈给运营' };
```

**用户答对了也被判 0 分，还被要求「反馈给运营」。**
而这个 bug 在练习关里完全看不见（那里一切正常），只在用户点进 Boss 时暴露。

### 5.3 处理方式

1. **加校验规则**（三处共用）：`bank-validator.ts` 里检查两个关卡集合的题目是否重叠
2. **加 CI 断言**：`tests/wiring.test.mjs` 第 6.4 节
3. **新建 `boss-questions.ts`**：6 道 Boss 专属题，只挂在 Boss 关

### 5.4 技术债 → ✅ 已解决（服务端客观题判分链路）

**当时的处理是「Boss 关用专属题」—— 一个绕过方案，代价是题库维护成本翻倍。**
本轮把它从根上解决了：**新增服务端客观题判分链路**，Boss 关不再需要专属题。

#### 为什么这是「从根上」而不是「再绕一层」

原缺口：Boss 关不下发 `localJudgeKey`（它在数学上等价于答案，下发即泄题），
而服务端**只有编程题（沙箱）一条判分入口** —— 于是 Boss 关的客观题
**用户答对也判 0 分**，100% 无法通过。

#### 新增的四段

| 段 | 文件 | 职责 |
|---|---|---|
| 端点 | `src/server.ts` → `/judge/objective` | 收「题号 + 作答」，**不走并发闸门**（毫秒级，占闸门反而误伤编程题） |
| 判分 | `src/judges/objective.ts` | 五种策略（exact/set/normalize/output/numeric）+ `sanitizeOutcome()` |
| 答案库 | `src/questions/answers.ts` | 三态查询 + 缓存（成功才缓存）；`mock-answers.ts` 内置样例 |
| 客户端 | `services/judge.ts` / `judge-client.ts` | `canJudgeServerSide()` + `submitObjectiveToJudge()` |

#### 三条不可松的纪律

1. **客户端/服务端判分口径零漂移**：`engine/judges/*` 与 `judges/objective.ts`
   对同一作答必须给出同一结论。由 `judge.test.mjs` 19.5 节 `CROSS_VECTORS`
   22 条向量强制 —— **这条自检立刻抓出过 `numeric` 的真实漂移**
   （答案对象形态两端不一致：客户端要 `{value,...}`、服务端按裸值处理）。
2. **答案绝不出现在返回体**：`sanitizeOutcome()` 在返回前抹掉 detail 里的正确答案。
3. **题型交叉校验**：客户端报的题型必须与题库一致，否则 400
   （否则「用户看到的题」和「被判的题」可能不是同一道）。

> 关于「专属题」：现在 Boss 关**仍用专属题**。这不是被迫，而是内容设计选择
> —— Boss 关的题应该综合多个知识点，与练习关的单点辨析题定位不同。
> 但**架构上它已不再必需**，将来想让 Boss 关复用练习题也不必改代码了。

## 6. 顺带修掉的自检缺陷

### 6.1 「测试文件自己记了一笔过时的账」

`tests/engine.test.mjs` 第 5/6 节原本写死：

```js
eq('会话题目数', s1.total, 4);
answerAll(s1, ['B', ['A', 'B', 'D'], ['65', 'int'], 'sum=9\ncount=3']);
```

题库一扩到 5 道题（知识点拆细），这两节整片红。
**红的原因和被测的会话状态机毫无关系** —— 纯粹是测试文件记了一个已经过时的题数。

改成从题目的 `localJudgeKey` **反推**「正确作答」和「错误作答」：

```js
const allCorrect = sessionQuestions.map(correctAnswerFor);   // 从判分依据反推
const totalQ = sessionQuestions.length;                       // 题数由数据决定
```

这样无论题库怎么改，这份自检都在测**同一件事**（会话状态机 + 星级 + Combo）。

### 6.2 同类问题：`pages.test.mjs`

原本写死 `3 关 / 9 星`，改成从题库派生：

```js
const CHAPTER_LEVEL_COUNT = bank.LEVELS.filter((l) => l.chapterId === 'c_ch01').length;
```

**原则：断言「关卡数」时应该去问题库，不该自己背一个数字。**

## 10. 本轮顺带发现并修掉的两个真实缺陷

它们不属于题库扩充，但都是在验证题库内容时暴露的，记录在此以免重复踩。

### 10.1 ⚠️ 生产入口根本跑不起来（最严重）

`judge-service/src/server.js` 曾是 `server.ts` 的**逐字节副本**，里面带着
`export type`、`: JudgeErrorCode` 这类 TS 语法。但 **Node 的类型剥离只对
`.ts/.mts/.tsx` 生效，对 `.js` 完全不生效** → `node src/server.js` 直接
`SyntaxError`。而 Dockerfile 的 `CMD` 与 `package.json` 的 `start`/`main`
都指向它 —— **生产起不来**。

**为什么此前 1199 项自检全绿也盖不住**：所有自检都 `import('server.ts')`
（走类型剥离），**从没验证过 `.js` 能否执行**。这是典型的「自己给自己发绿牌」。

**修法**：`server.ts` 作唯一真源（含类型），`server.js` 改薄垫片
（注册后缀补全钩子 + 逐名重导出）。配套：Dockerfile 升到 `node:22`，
`engines.node >= 22.6`。自检用 `judge.test.mjs` 19.12 节**实跑**卡住。

### 10.2 ⚠️ 新端点的空作答被回成 500

`precheckStatus()` 靠**消息文案**把「调用方的错」纠正成 4xx，
它的词表是给 `/judge`（代码提交）写的。新增 `/judge/objective` 后，
它的预检文案是「作答为空」—— 不在词表内 → **回 500**，
重新踩了「空输入被判服务端故障」的坑（前端给出无意义重试按钮 + 污染 5xx 告警）。

**修法**：词表补全 **+** 加结构性防线 —— `judge.test.mjs` 19.13 节遍历
**两个端点所有已知的预检失败路径**，断言一律 4xx（并反向断言真正的内部故障仍是 5xx）。
靠结构而非靠人记文案。

### 10.3 顺带记一条验证教训

`judge.test.mjs` 19.12 最初用 **spawn 子进程**去加载入口，结果在 Windows 上
得到 `EBUSY`（运行中的 `node.exe` 被锁）→ `status=null`、错误信息为空，
**看不出是环境问题还是被测代码的问题**。改为**进程内 `import()`** 后可靠。
（这是本项目已记录过的 Windows 坑，又踩了一次。）
