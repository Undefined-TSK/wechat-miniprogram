## 1. 判题链路全貌

```
小程序                          云函数（中转）              判题服务                一次性沙箱容器
  │                                │                        │                        │
  ├─ 取题 ────────────────────────▶│                        │                        │
  │◀── ClientQuestion（无 answer） ─┤                        │                        │
  │                                │                        │                        │
  ├─ 用户写代码（code-editor）      │                        │                        │
  │                                │                        │                        │
  ├─ submitToJudge(req) ──────────▶│ 注入 token             │                        │
  │                                ├───────────────────────▶│                        │
  │                                │                        ├─ precheck（代码大小）    │
  │                                │                        ├─ 幂等检查（缓存命中即回） │
  │                                │                        ├─ 限流检查               │
  │                                │                        ├─ 编译容器 ─────────────▶│ ① 编译
  │                                │                        │◀─ 产物 docker cp ───────┤    （10s/512MB）
  │                                │                        ├─ 运行容器 × N ─────────▶│ ② 逐测试点运行
  │                                │                        │◀─ 退出码/信号/耗时/内存 ─┤    （1s/256MB）
  │                                │                        ├─ 分类 → AC/WA/CE/…      │
  │                                │◀── JudgeResponse ──────┤                        │
  │◀── 判题结果 + 解析 ─────────────┤   （剥离 systemNote）   │                        │
  │                                │                        ├─ finally: 清理临时目录   │
```

三个关键设计点：

1. **前端不持自建服务 token**。token 只存在于云函数环境变量。前端拿到的只是云函数返回体。
2. **用户代码只能通过文件进容器**。以只读方式挂载到 `/box`，绝不进命令行参数——从根上排除命令注入。
3. **编译与运行分容器**。产物经宿主 `docker cp` 中转，运行容器里**没有编译器**。

## 2. 跨端契约（唯一来源）

### 2.1 为什么契约要有两份、又必须逐字节一致

小程序端不能 `import` 主工程外的路径，所以契约文件在两边各放一份：

```
miniprogram/services/judge-contract.ts   ← 客户端
judge-service/src/contract.ts            ← 判题服务
```

契约分家之后极易出现的故障是：服务端加了新 verdict，客户端映射没跟上 → **UI 显示 null**，没有报错。
所以用自动比对替代人工纪律：

```bash
cp miniprogram/services/judge-contract.ts judge-service/src/contract.ts
node tests/judge.test.mjs   # 会做 SHA-256 比对，不一致直接失败
```

### 2.2 请求 / 响应

```ts
JudgeRequest {
  submissionId: string   // 幂等键，同一 ID 重复提交必须返回同一结果
  questionId: string
  type: string
  language: 'c' | 'cpp' | 'python'
  code: string
  limits?: JudgeLimits   // 只能收紧，不能放宽（服务端还会夹到硬上限）
}

JudgeResponse {
  submissionId, verdict, score, passed, total,
  compileMessage?,        // CE 时才有
  cases: JudgeCaseResult[],
  totalMs, finishedAt, cacheHit
}
```

### 2.3 资源上限的两层夹取

```ts
DEFAULT_LIMITS  = { compileMs: 10000, runMs: 1000, memoryMB: 256, outputBytes: 1MB, maxProcs: 64 }
HARD_LIMITS     = { compileMs: 10000, runMs: 2000, memoryMB: 512, outputBytes: 1MB, maxProcs: 128 }
```

`clampLimits()` 的逻辑是「题目配额优先，请求只能收紧」。
**服务端必须再调一次**——否则客户端传个超大 limits 就能绕开资源限制。这条有专门的测试覆盖。

## 3. 12 项沙箱加固的落点

| # | 加固项 | 具体实现 | 自检断言 |
|---|---|---|---|
| 1 | seccomp 白名单 | `--security-opt seccomp=/etc/judge/seccomp-judge.json`，默认动作 `SCMP_ACT_ERRNO` | 白名单内不含 ptrace/socket/connect/mount/unshare/setns/reboot/bpf/kexec_load |
| 2 | 非 root | `--user 1000:1000` + `no-new-privileges` + `--cap-drop ALL` | 三条参数均在 |
| 3 | cgroup v2 | `--cgroupns private`、`--memory`、`--memory-swap`（**相等，关 swap**）、`--pids-limit` | memory 与 memory-swap 必须相等 |
| 4 | 编译/运行分容器 | 两阶段各自 buildPlan，产物 `docker cp` 中转 | 容器名不同；**编译失败时运行阶段 0 次调用** |
| 5 | 代码大小上限 | `precheck()` 单文件 64KB，UTF-8 实算 | 超长代码被拒 |
| 6 | 编译超时 | `--ulimit -t` + Node 侧墙钟定时器 `docker kill` | 超时判 CE 并带提示 |
| 7 | 禁 ptrace | seccomp 不列 + `cap_drop ALL` 双保险 | profile 断言 |
| 8 | 禁用网络 | `--network none` | 参数断言 |
| 9 | 只读根 fs + 独立 tmpfs | `--read-only`、`--tmpfs /tmp:noexec`（**两阶段都开**）、源码 `:ro` 挂载、产物独立只读可执行挂载 `/box-artifact` | tmpfs 恒 noexec；产物不在 tmpfs |
| 10 | 输出上限 | 包装脚本 `head -c` 逐流截断，超限判 OLE | 输出超限优先于答案比对 |
| 11 | 频率限制 | `ratelimit.ts`，30 次/分、300 次/日 | 限流生效 + **被拒请求不消耗配额** |
| 12 | 节点网络隔离 | compose 只绑 `127.0.0.1`；生产独立安全组 | compose 断言 |

### 第 9 项的细节：noexec 与产物挂载为什么必须拆开

这是本轮修掉的一个真实漏口。原来的写法是 `--tmpfs /tmp:noexec=false`（两个阶段都是），
意味着**用户代码可以往 /tmp 里写一个二进制然后执行它**——绕过了「代码只能从源码编译」这条约束。

修法是拆开两件事：

| 需求 | 落点 | 属性 |
|---|---|---|
| 编译器要往 /tmp 写产物 | `/tmp` tmpfs | 可写，**noexec** |
| 运行时要执行产物 | `/box-artifact` 独立挂载 | **只读**，可执行 |

两个关键认识：

1. **「写入可执行文件」不等于「执行文件」。** 编译阶段需要的是前者——
   gcc 执行的是 `/usr/bin/gcc`，它读 `/box/main.c`，写 `/tmp/box.out`，
   全程不需要执行 /tmp 里的东西。所以 noexec 不影响编译。
   早期以为「编译阶段要放开 noexec」是把这两个概念混了。
2. **产物必须只读挂载。** 否则用户代码可以先执行一遍、再篡改产物文件
   （比如把它换成一个直接输出期望答案的假程序），下一个测试点就跑的是假程序。

**连带的清理责任**：产物目录是 workDir 的**同级** `.artifacts`（不能放 workDir 里——
workDir 是只读挂载，混在一起会让整个工作目录变可执行）。
所以 `LocalWorkspace.cleanup()` 必须**同时删掉这两个目录**，
否则会残留大量编译产物——判题服务撑爆磁盘最经典的成因。
自检里有 `artifactDirFor()` 的断言盯着这个路径推导。

### 三个容易做错、已经踩过的点

**① `--memory-swap` 必须等于 `--memory`。**
只设 `--memory` 的话，超内存会走 swap 而不是触发 OOM，结果是程序变得极慢然后被判成 TLE。
用户拿到「超时」去优化算法复杂度，方向完全错。所以这一条专门有断言。

**② 编译失败后绝不能进入运行阶段。**
共用容器时，编译失败后如果还去跑产物，会跑出**上一次提交的残留二进制**——
用户看到的是别人的输出，还以为是自己的代码有问题。所以 `runner.compile()` 返回失败即终止，
测试里有一条专门断言此时运行阶段调用次数为 0。

**③ SIGKILL 有双重语义。**
它既可能是 OOM Killer（内存超限），也可能是运维强制终止。靠「峰值内存 ≥ 上限 × 0.85」区分。
判错方向后果同样严重：用户会去优化一个不存在的内存问题。

## 4. 判题结论分类（8 种状态码）

| 状态码 | 文字 | 触发条件 | 用户该做什么 |
|---|---|---|---|
| `accepted` | 通过 | 全部测试点输出匹配 | — |
| `wrong-answer` | 答案错误 | 输出与期望不一致 | 检查逻辑 |
| `compile-error` | 编译错误 | 编译容器退出码非 0 | 看编译器信息 |
| `runtime-error` | 运行时错误 | 致命信号（SEGV/FPE/ABRT）或非零退出码 | 检查越界/除零/空指针 |
| `time-limit-exceeded` | 运行超时 | 墙钟超时或 SIGXCPU | 检查死循环与复杂度 |
| `memory-limit-exceeded` | 内存超限 | SIGKILL 且峰值内存接近上限 | 检查数组大小 |
| `output-limit-exceeded` | 输出超限 | 输出被截断 | 检查调试打印/死循环输出 |
| `system-error` | 系统错误 | SIGSYS、判题设施异常 | 重试，或反馈我们 |

### 判定优先级（顺序不能换，有测试锁定）

```
① 编译失败          → CE     编译不过谈不上运行
② 输出超限          → OLE    先于答案比对：输出爆炸时比对结果无意义
③ 墙钟超时          → TLE
④ SIGXCPU           → TLE
⑤ SIGKILL + 高内存  → MLE
   SIGKILL + 低内存  → RE
⑥ 其他致命信号      → RE     （SIGSYS 例外 → SE）
⑦ 退出码非 0        → RE
⑧ 输出比对          → AC / WA
```

**一个重要的归责决定**：`SIGSYS` 归到 `system-error` 而不是用户错误。
SIGSYS 意味着进程调用了 seccomp 白名单外的系统调用——通常**是我们的白名单缺了调用**。
让用户背这个锅是错的。这条在分类函数里写死了理由，避免后人「顺手统一成 RE」。

### 部分通过的计分口径

```
score = 通过测试点数 / 总测试点数
但 correct 恒为 false
```

为什么：编程题里「过了 3/5 个点」就是没做对。
所以 `correct=false, partial=true, score=0.6`——星级会认这 0.6，但 Combo 不递增。

## 5. 防泄题设计

编程题的测试点是**服务端资产**，这是与选择题最大的不同：选择题的答案泄漏一次就完了，
编程题的测试点泄漏可以让人「针对测试点硬编码」，写出对这个题完全无效但能满分的代码。

三道防线：

1. **测试点永不下发**。`judge_plans` 集合只在判题服务侧读取。
2. **隐藏测试点不回传任何 preview**。`buildPreviews()` 是唯一执行点，hidden 时返回空对象。
   自检里有一条专门断言 `JSON.stringify(preview) === '{}'`。
3. **公开点通过时不回传实际输出**。少一个「用输出反推测试点」的面。

另外 `validatePlan()` 会对「没有任何隐藏测试点」的计划给出告警——
不阻止发布，但提醒运营补隐藏点。自检里把这条作为硬性要求：
**每个判题计划必须至少有一个隐藏测试点**。

## 6. 样例编程题与测试点设计

两道样例题的测试点是**有意设计**的，不是随手写的：

### 题 5：读入 n，输出 1..n 的累加和

| # | 输入 | 期望 | 隐藏 | 考察点 |
|---|---|---|---|---|
| 1 | `1` | `1` | | 边界：循环写错（多算/少算一轮）在这里暴露 |
| 2 | `5` | `15` | | 基础功能 |
| 3 | `100000` | `5000050000` | | **核心考点**：和超过 int 上限（约 2.1×10⁹） |
| 4 | `99999` | `4999950000` | ✅ | 防针对公开点硬编码 |

题 3 是这道题真正的考点：用 `int` 的同学逻辑完全正确，但会得到错值。
所以解析里明确写了「很多同学的逻辑完全正确，却因为类型选小而拿到错误的输出」。

### 题 6：读入若干整数直到 EOF，输出最大值

| # | 输入 | 期望 | 隐藏 | 考察点 |
|---|---|---|---|---|
| 1 | `42` | `42` | | 单个数：循环体一次都不执行也要正确 |
| 2 | `3 9 2 7` | `9` | | 常规多值 |
| 3 | `-5 -1 -9` | `-1` | | **核心陷阱**：初值写 0 的同学在这里错 |
| 4 | `100 1 2 3` | `100` | ✅ | 最大值在开头，防「只在末尾更新」的实现 |
| 5 | `1 2 3 100` | `100` | ✅ | 最大值在结尾 |

## 7. 客户端接线

### 7.1 判分调度（`services/judge.ts`）

```
题目带 localJudgeKey？ ─── 是 ──▶ 本地判分器（练习关）
        │
        否
        ▼
  题型映射策略
   ├─ sandbox  ──▶ submitToJudge() → 判题服务
   ├─ ai       ──▶ 提示 Phase 5（明确标注「本次不计分」）
   └─ 其他     ──▶ 判为「题目配置异常」
```

最后那条分支值得说明：非练习关的选择/填空类题**本应带 `localJudgeKey`**。
如果落到了这里，说明题目配置有问题。给用户的文案是
「这不是你的问题，本次不计分」——不能让用户为我们的配置错误买单。

### 7.2 策略映射表的约束

客户端拿不到 `judge.strategy`（已剔除），所以按题型查表。
**这张表必须与 `bootstrap.ts` 的 `renderer.judgeStrategies` 一致**——
接线自检会逐个题型核对，不一致直接报出来。

### 7.3 编程题渲染器

`code-editor` 用原生 `textarea`，不是 WebView + CodeMirror。取舍：

- 拿到的是**闭环价值**：编程题现在能作答、能判分
- 付出的是**没有语法高亮**与**光标级编辑能力**

⚠️ 一个必须写清的平台能力边界：
小程序 `textarea` 原生组件**不支持程序化设置光标位置**（没有可写的 selectionStart）。
所以「插入缩进」只能做成**整行粒度**（给光标所在行加 4 空格），做不了 IDE 那种光标处插入。
这不是偷懒，是平台限制。要真正的光标级编辑必须上 WebView 编辑器。

**升级路径是干净的**：把 `textarea` 换成 `web-view`，把 change 事件桥接过来，
`code-editor` 的对外契约（properties + `change` 事件）一行都不用改。
这正是把渲染器做成独立组件、只暴露 properties/event 的收益。

### 8.0 已交付的部分

HTTP 入口、HMAC 鉴权、Redis 限流、云函数中转**都已交付**（见 §11–§14）。

### 8.1 沙箱镜像（✅ 已交付构建脚本）

`judge-gcc:13-slim` 与 `judge-python:3.12-slim` 是自建镜像，Docker Hub 上没有。
**构建脚本已交付**：`judge-service/images/`（两个 Dockerfile + `build.sh`）。

```bash
npm run sandbox:build      # 构建 + 自动校验
npm run sandbox:verify     # 只校验，不构建
```

**为什么必须自建而不能用公共镜像**：这是全系统唯一「主动执行陌生人代码」的地方。
公共镜像自带 curl/wget 等外联工具，会让「禁网」这条加固退化成单点依赖——一旦
禁网配置被改错，出网能力立刻复活且无人察觉。自建镜像里这些工具**根本不存在**，
两层防线互相独立。

**构建脚本会校验什么**（构建完不算完，每条要求都必须能被自动检查）：

| 校验项 | 为什么 |
|---|---|
| `curl`/`wget`/`nc`/`ssh` 不存在 | 禁网第二道防线 |
| 默认 UID = 1000 | 与 `policy.ts` 的 `--user 1000:1000` 强绑定 |
| 镜像名与 `policy.ts` 的 `LANG_TABLE` 一致 | 不一致会在**用户提交时**才炸，不是部署时 |
| gcc 镜像能 `-static` 链接 | 编译命令带 `-static`，缺 `libc.a` 会编译失败 |
| python 镜像 `import socket` 失败 | 网络模块已删除 |
| python 镜像无 pip | 有 pip 就能装回网络库 |
| python `PYTHONHASHSEED=0` | 不关则 set/dict 遍历顺序不稳定 → **判题结果不可复现** |

**Python 镜像的额外处理**（攻击面比 C 大得多）：删掉 `socket`/`ssl`/`http`/`urllib`/
`ftplib`/`smtplib`/`xmlrpc` 等网络模块，删掉 pip/setuptools/wheel。
理由同上——禁网是容器级的，删模块是镜像级的，两层独立。

### 8.2 三个运维决策（已给出结论，无需用户拍板）

> **说明**：原版把这三条列为「待决策」，但它们是纯技术判断，且在编码阶段就有明确正确的答案。
> 把它们抛给非技术决策者是不合理的。以下为**已定结论 + 理由**，改配置时照此执行即可。

| 决策 | 结论 | 为什么 |
|---|---|---|
| 控制面如何访问 Docker | **docker-socket-proxy**（直挂 socket 仅限本机开发） | 判题服务是全系统**唯一执行陌生人代码**的组件，被攻破概率最高。直挂 socket 等于把宿主机 Docker 交给最危险的进程；proxy 只放行 `create/start/kill/inspect` 四类调用 |
| token 从哪来 | **初期环境变量**，上线前切密钥管理服务 | 环境变量够用且零成本；但它是明文躺在配置文件里，多人协作或上了云之后要换密钥管理。**这一条是纯运维动作，不影响代码** |
| 是否公网暴露判题节点 | **绝不**。走内网安全组 | 鉴权是第二道防线，不是第一道。公网暴露等于把攻击面从「内网」扩大到「全球」，任何鉴权实现的疏漏都会被立刻扫描到 |

**这三条都不需要用户理解或决策**——它们是实现细节，由开发者按上表执行。

### 8.3 部署拓扑（与本地编排的差异）

本地 `docker-compose.yml` 直挂 `/var/run/docker.sock`，**仅限本机开发**。
生产按 §8.2 的结论走 docker-socket-proxy，只放行四类调用：

| 层级 | 方案 | 隔离强度 |
|---|---|---|
| 仅本机开发 | 直挂 socket | 最弱（可用，因为不对外） |
| **生产（已定）** | **docker-socket-proxy** | 中（够用，成本低） |
| 未来演进 | 控制面与判题节点分离，远端 API 调度 | 最强（改造量大，非当前必要） |

无论哪种，**判题节点必须放进独立安全组，只接受来自业务层的鉴权调用**。

### 8.4 seccomp profile 必须校准（最高优先级技术债）

**这一条是真正需要用户知道的事**，但也不需要用户做技术决策——只是需要知道「有件事必须先做完，否则会持续收到错误的用户反馈」。

`etc/seccomp-judge.json` 是**基线白名单，不是最终版本**。
seccomp 是 Linux 的「系统调用白名单」机制：我们列一份「允许用户代码调用哪些系统能力」的清单，
不在清单上的一律拒绝。安全性靠它，但清单写漏了会误伤正常代码。

**漏了会怎样**：用户正确代码被拒绝执行 → 判成 CE（编译错误）或 RE（运行错误）。
用户看到「我的代码明明是对的」→ 反复提交 → 我们却什么都查不出来，因为错误被归到了用户头上。

**✅ 校准工具已交付**（`judge-service/scripts/seccomp-calibrate.mjs`），流程分三步：

```bash
# 1. 看校准计划（不碰 docker，确认要跑哪些题）
npm run seccomp:plan

# 2. 真跑：用 SCMP_ACT_LOG（放行但记录）的 profile 跑 10 道校准题
node judge-service/scripts/seccomp-calibrate.mjs

# 3. 收集内核日志后分析（需要 root，命令由脚本打印）
npm run seccomp:report -- <日志文件>
```

**核心设计：为什么用 `SCMP_ACT_LOG` 而不是 `SCMP_ACT_ALLOW`**

| 做法 | 结果 |
|---|---|
| `SCMP_ACT_ALLOW` | 全放行，**日志什么都没有** —— 收集不到任何信号 |
| `SCMP_ACT_ERRNO`（正式配置） | 被拦的调用直接失败，程序崩了，但**不知道为什么崩** |
| **`SCMP_ACT_LOG`（校准用）** | **放行但记录** —— 程序正常跑完，同时把「本该被拦的调用」全记下来 |

这是校准能成立的关键：我们需要的是「哪些调用是必需的」这个**信号**，
而不是「拦住它们」这个**行为**。校准完把日志里实际出现、但白名单没有的调用补进去，
再把 `defaultAction` 换回 `ERRNO`。

**10 道校准题的分工**（在 `src/questions/calibration-samples.ts`，每题都标注了用途）
——不同 C 库函数触发完全不同的系统调用，只跑 hello world 只能覆盖 3 个：

| 题 | 专门暴露什么 |
|---|---|
| cal-01 hello | 最小基线（execve/write/exit_group/brk） |
| cal-02 scanf | 标准输入的 read/ioctl/fstat |
| cal-03 大块 malloc | 超 MMAP_THRESHOLD 时走 mmap 而非 brk |
| cal-04 字符串 | 验证 strtod/strtok 无新调用（对照项） |
| cal-05 qsort | 大数组 + 栈增长触发 mremap |
| cal-06 数学库 | **暴露编译命令缺 `-lm`**（已修） |
| cal-07 文件 IO | openat/unlink（只读根 fs 下应只有 /tmp 可写） |
| cal-08 fork | **`clone3`** —— glibc 2.34+ 优先用它，老 profile 最常漏 |
| cal-09 计时 | clock_gettime/nanosleep |
| cal-10 深递归 | 栈自动增长（mremap）+ 信号处理路径 |

**脚本还会区分三类，而不是笼统报「缺失」**：

- **危险调用**（socket/ptrace/mount…）→ 单独警示为**安全事件**。
  绝不能混进「建议补充」清单，否则人工 review 时可能顺手加进白名单，造成安全倒退。
- **缺失调用** → 建议逐条确认后补充，并直接给出可合并的 JSON 片段。
- **未知编号** → 老实报 `syscall#7000` 让人去查，**不瞎猜**。

**这件事不做完，编程题上线会持续收到「明明对却判错」的反馈，且无法从日志区分。**
→ 工具已就绪，剩下的是在真机上跑一次（需要 docker + root 读内核日志）。

## 11. HTTP 接入层（`src/server.js`）

> ⚠️ **入口文件的分工（本轮修正，务必不要回退）**
>
> | 文件 | 角色 | 是否含 TS 类型语法 |
> |---|---|---|
> | `src/server.ts` | **唯一真源**，完整实现 + 类型 | 是 |
> | `src/server.js` | **薄垫片**（生产入口） | **否（绝不能有）** |
>
> `server.js` 只做两件事：① 注册后缀补全解析钩子（让 `from './auth'` 这类
> 无扩展名导入可解析）；② **逐名重导出** `server.ts` 的全部导出，
> 使 `import('server.js')` 与 `import('server.ts')` 拿到完全一致的模块形状。
>
> **为什么不能再用「两份逐字节一致」**：Node 的类型剥离**只对 `.ts/.mts/.tsx` 生效**，
> 对 `.js` 完全不生效。旧做法把 `server.ts` 逐字节复制成 `server.js`（带着
> `export type`、`: JudgeErrorCode`），于是 `node src/server.js` **直接 SyntaxError**
> —— Dockerfile 的 `CMD` 与 `package.json` 的 `start`/`main` 都指向它，**生产根本起不来**。
> 更糟的是此前所有自检都 `import('server.ts')`，**从没验证过 `.js` 能否执行**，
> 1199 项全绿却盖不住这个洞。现在由 `judge.test.mjs` 第 19.12 节**实跑**卡住：
> 入口可加载 + 导出名与 `.ts` 完全一致 + 不含 TS 语法 + 代码 < 120 行。
>
> **垫片为什么必须用动态 import + 逐名重导出**：静态 `export * from './server.ts'`
> 会在**模块加载期**就解析 `server.ts` 的依赖树，而此时 `register()` 注册的解析钩子
> 还没有机会介入 —— 表现为 `Directory import './auth' is not supported`。
>
> **配套**：Dockerfile 基础镜像必须是 `node:22`（Node 20 无类型剥离），
> `engines.node >= 22.6`。
>
> **验证陷阱**：`judge.test.mjs` 19.12 刻意用**进程内 `import()`** 而不是 spawn 子进程
> —— Windows 上 `spawn(process.execPath)` 会 `EBUSY`（运行中的 node.exe 被锁），
> 表现为 `status=null`、错误信息为空，看不出是环境问题还是被测代码的问题。

### 11.1 为什么 HTTP 层必须与判题编排层分开

| 层 | 文件 | 可注入点 | 自检方式 |
|---|---|---|---|
| HTTP 语义 | `src/server.ts`（`server.js` 是垫片） | `submit` 假实现 | 真实 http 请求 + 假判题 |
| 判题编排 | `src/judges/index.ts` | `SandboxRunner` / 存储 | 假执行器，无 docker |
| 沙箱策略 | `src/sandbox/policy.ts` | 无（纯函数） | 直接断言生成的参数 |
| 客观题判分 | `src/judges/objective.ts` | 无（纯函数） | 与客户端判分器跑**同一组向量**比对 |

分开的收益很直接：**HTTP 层的 bug 不会掩盖判题层的 bug，反之亦然**。
如果混写，一个「状态码映射错了」的问题会被人误以为是「判题逻辑错了」，排查方向从一开始就偏。

### 11.2 路由

| 路径 | 方法 | 鉴权 | 语义 |
|---|---|---|---|
| `/judge` | POST | **必须** | 提交**编程题**判题（沙箱链路） |
| `/judge/objective` | POST | **必须** | 提交**客观题**判题（选择/填空/程序输出/数值） |
| `/healthz` | GET | 无 | liveness：进程活着就 200，不查任何依赖 |
| `/readyz` | GET | 无 | readiness：只在**饱和**时 503 |
| `/metrics` | GET | 无 | 最小指标（inflight / uptime / 降级状态），**不含用户维度** |

尾斜杠会被规范化（`/judge/` ≡ `/judge`），且规范化发生在**验签之前**——
次序反了会让所有带尾斜杠的请求 401（签名对 `/judge` 算、校验传 `/judge/`）。

#### 为什么客观题需要独立端点（而不是复用 `/judge`）

| | `/judge`（编程题） | `/judge/objective`（客观题） |
|---|---|---|
| 判分依据 | 测试点（输入→期望输出） | 答案（标量/数组） |
| 是否起容器 | 是（编译 + 运行 + 资源限制） | **否**（纯内存比对） |
| 是否走并发闸门 | 是（每个容器都是重资源） | **否**（毫秒级，占闸门反而误伤编程题） |
| 客户端送什么 | 代码 | 题号 + 作答（**不含答案**） |

**这条链路是本轮新增的，动机是一个真实缺陷**：
Boss 关/挑战关**不下发** `localJudgeKey`（它在数学上等价于答案，下发即泄题），
而此前服务端只有编程题（沙箱）一条判分入口 —— 于是 **Boss 关的客观题用户答对也判 0 分**，
100% 无法通过。修法是补上这条链路，而不是把答案下发回客户端。

#### 请求 / 响应示例

```jsonc
// 请求（客户端只送题号与作答，字段白名单：submissionId/questionId/type/answer）
{
  "submissionId": "sub_abc",
  "questionId": "q_c_0054",
  "type": "single-choice",
  "answer": "B"
}

// 响应（⚠️ detail 已由 sanitizeOutcome 抹掉正确答案）
{ "ok": true, "result": { "correct": true, "partial": false, "score": 1,
  "detail": "回答正确", "layer": "remote", "strategy": "exact" } }
```

**错误语义**（与三态纪律一致）：
- 题库**明确说没有**这道题 → 404 `question-not-found`
- 题库**此刻查不到**（网络/超时） → 500 `internal`（可重试）
- 客户端**题型与题库不一致** → 400（说明客户端版本旧，或有人手工构造请求；
  按题库判分会导致「用户看到的题」和「被判的题」不是同一道）

### 11.3 六条必须做对的实现

| # | 做法 | 做错的后果 |
|---|---|---|
| ① | 先看 `Content-Length`，超限直接 413 并 `req.resume()` | 只靠流式累计会被「声明 10 字节但持续发送」拖死；而 `req.destroy()` 会让客户端看到 ECONNRESET 而不是我们的 413 |
| ② | **读完整原始字节后立刻算 SHA-256**，再解析 JSON | 先 `parse` 再 `stringify` 会改变键序/空白/Unicode 转义 → 哈希必不同 → 全部 401 |
| ③ | 并发饱和返回 503 + `Retry-After`，**不排队** | 排队会让请求撞上网关超时（用户看到「无响应」），且积压请求持续吃内存 |
| ④ | 请求体读取设超时 | 慢速发送（slowloris）几百个半开连接就能拖住服务 |
| ⑤ | 错误响应体只含 `code`/`message`，stack 与路径只进日志 | 泄漏内部结构给攻击者 |
| ⑥ | SIGTERM 后停接新连接 → 等在途完成 → 关 Redis | 滚动更新时正在判的提交被硬杀，用户看到「服务内部错误」 |

### 11.4 错误码 → HTTP 状态码

| 错误码 | 状态 | 说明 |
|---|---|---|
| `unauthorized` | 401 | 缺字段 / token 不符 / 时间戳超窗 / 签名不符 / nonce 重放 |
| `forbidden` | 403 | 越权提交 |
| `rate-limited` | 429 | 频率超限，**带 `Retry-After`** |
| `payload-too-large` | 413 | 请求体或代码超限 |
| `unsupported-language` | 400 | 语言不支持 |
| `question-not-found` | 404 | 题目不存在或无判题计划 |
| `session-expired` | 410 | 场次已结束（资源存在但不可用，故 410 而非 404） |
| `busy` | 503 | 队列饱和，**带 `Retry-After`** |
| `internal` | 500 | 未分类 / 输入非法（见下） |

**429 与 503 必须分开**：前端对 429「等冷却再试」，对 503「换实例 / 退避更久」。
合并成一个码会让整套重试策略失灵。

**输入非法被纠正为 400**：`precheck()` 是跨端函数，受契约错误码约束，
「空代码」只能报 `internal`（映射 500）。`server.js` 的 `precheckStatus()` 按消息语义
把它纠正成 400。不纠正的后果有两个：前端会给出「重试」按钮（空代码重试一万次还是空代码），
以及监控把用户传坏数据算进 5xx 故障率，导致真出事时告警被噪声淹没。

> ⚠️ **这张表靠「消息文案」识别，因此新增端点时必须同步扩词表。**
> 新增 `/judge/objective` 时它的文案是「作答为空」，未在词表内 → 空作答被回成 **500**，
> 重新踩了同一个坑。现在有两条防线：
> ① 词表补全（`代码为空|作答为空|缺少|必须是字符串|必须是数组|不支持`）；
> ② `judge.test.mjs` 第 19.13 节**遍历两个端点所有已知的预检失败路径**，
> 断言一律 4xx（并反向断言真正的内部故障仍是 5xx）。靠结构而非靠人记文案。

### 11.5 liveness 与 readiness 为什么必须分开

| | `/healthz` | `/readyz` |
|---|---|---|
| 检查什么 | 什么都不查 | 只查「还有并发容量」 |
| 什么时候失败 | 进程死了 | 饱和时 |
| 失败后果 | k8s 重启进程 | 负载均衡摘流量 |
| Redis 挂了 | **仍 200** | **仍 200** |

两条都不能动的判断：

- **Redis 挂了不算 not ready**。限流与重放拦截都有降级路径，判题本身仍能跑。
  把依赖故障一律当 not ready，会让「Redis 抖 5 秒」升级成「所有判题节点被摘」。
- **Redis 挂了也不该重启进程**。混淆 liveness 与 readiness 的经典后果就是
  「Redis 抖一下，全部判题节点被重启」。

## 12. 鉴权协议（token + HMAC 签名 + nonce）

### 12.1 为什么不用裸 token

| 方案 | 问题 |
|---|---|
| 裸 token | 每个请求原样传输。一旦落到日志/代理/抓包，攻击者能无限期伪造提交 |
| Basic Auth | 同上，且 base64 不是加密 |
| **token + HMAC** | 请求体被改则签名不匹配；时间戳 + nonce 让抓到的签名只能在极短窗口内用一次 |

### 12.2 签名串拼法（契约）

```
v1 \n METHOD \n PATH \n TIMESTAMP \n NONCE \n SHA256_HEX(BODY)
```

- 分隔符用 `\n` 而不是 `|`：路径 query 等字段可能含任意可打印字符，
  固定不可打印分隔符能从根上避免「字段值带分隔符造成歧义」这类拼接漏洞。
- 签的是 body 的 **SHA-256 哈希**而不是 body 本身：body 可能 64KB，没必要每次参与 HMAC。

### 12.3 三层验证目标

| 层 | 证明什么 | 不能防什么 |
|---|---|---|
| token | 「调用方是业务层」 | 重放 |
| HMAC 签名 | 「请求体由持 token 者构造且未被改」 | 重放 |
| nonce 独占 | 「这个请求没被重放过」 | — |

任意一层被绕过都是事故。token 比较也走**常量时间**（先各自 SHA-256 再比较）。

### 12.4 校验顺序（不能换）

```
① 字段齐全 → ② 时间戳格式 → ③ 时间窗（双向） → ④ token → ⑤ 签名 → ⑥ nonce 登记
```

两个刻意设计：

- **时间窗双向**。只查「太旧」不够：时间戳在未来同样危险，等于给攻击者更长的重放窗口。
- **只有验签通过才登记 nonce**。反过来的话攻击者可以不带有效签名就消耗 nonce 空间
  （廉价 DoS），还能把合法用户的 nonce 提前占掉。

### 12.5 nonce 重放：并发安全来自「独占写入」而不是「先查后写」

```
✗  if (await has(nonce)) return replay;  await set(nonce);
   两个并发请求可同时通过 has()，然后都 set() 成功 → 重放成功

✓  const ok = await redis.command(['SET', key, '1', 'NX', 'PX', ttl]);
   return ok !== null;      // nil = 已被用过
```

内存实现之所以单进程内安全：Node 单线程，只要 check-and-set 之间**没有 await** 就不会被打断。
自检里有一条**并发重放**用例（`Promise.all` 四次 `claim`，只允许一次成功），
顺序重放的用例过不了它——先查后写的实现会被它抓住。

### 12.6 降级方向：重放拦截与限流**相反**

| | 主存储不可用时 | 理由 |
|---|---|---|
| 限流 | **fail-open**：放行 + 告警 | 判题算力是可恢复成本；功能全挂是用户可感知故障 |
| 重放拦截 | **fail-degraded**：退回单实例内存 | 放行重放是安全事件，不是成本事件 |

**不要抄另一个的方向。** 这是本项目最容易「看起来对称其实写反」的一处。

## 13. Redis 线

### 13.1 客户端为什么是最小自研

我们的需求只有四个命令：`SET NX PX`、`EVAL`、`MGET`、`QUIT`。
为一个上万行的通用客户端引入依赖，等于给「处理不可信输入的服务」增加一大块
供应链与攻击面。`src/redis/client.ts` 只实现 RESP2 的 5 种类型。

| 实现要点 | 说明 |
|---|---|
| 只提供 `command(args: string[])` | **不提供发原始字符串的接口** → 「参数含 CRLF 导致命令注入」在架构上不可能 |
| 长度按**字节**算 | 用字符数会让中文参数被截坏 |
| 自动重连 + 指数退避 + 抖动 | 避免多实例同时重连把 Redis 打死 |
| 命令超时（默认 3s） | Redis 卡住时不能把 HTTP 请求一起卡住 |
| 失败即 reject | 由上层决定 fail-open 还是 fail-closed |

### 13.2 限流计数器：为什么必须用 Lua

```lua
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('PEXPIRE', KEYS[1], ARGV[1]) end
-- 补设：上次脚本中断可能把 key 留成无过期时间 → 该用户被永久限流
if redis.call('PTTL', KEYS[1]) < 0 then redis.call('PEXPIRE', KEYS[1], ARGV[1]) end
```

两种朴素写法都是错的：

| 写法 | 后果 |
|---|---|
| `INCR` 然后 `PEXPIRE`（两步） | 两命令之间断连 → key **永不过期** → 用户被永久限流。只在网络抖动时出现，本地测不出来 |
| 每次都 `PEXPIRE` | 窗口被无限续期 → 用户持续提交就永远不重置。那不是限流，是惩罚 |

### 13.3 「先检查后计数」的配额口径（沿用 v0.2 决策）

被拒绝的请求**不消耗配额**。先计数会把被拒请求也算进配额，
用户越重试恢复得越慢——那不是限流，是惩罚。

### 13.4 同步接口 vs 异步存储的张力

`RateCounter` 接口是同步的（业务层不该知道存储是不是异步的），而 Redis 只能异步取。
处理方式是显式两层：

1. `RedisRateCounter.incr()` 同步返回本地兜底值（可能偏乐观），同时异步发 `EVAL`。
2. `JudgeService.submit()` 在限流判定**之前** `await prefetch(userId)`，
   用 `MGET` 把权威计数拉回本地 → 多实例下的判定是准确的。

> ⚠️ **`prefetch` 里有一个不报错的坑**：本地兜底表的键必须用 **bucket**（`rl:m:<userId>`），
> 不能加 Redis 前缀。用前缀会让 `prefetch` 写入 `local['judge:rl:rl:m:u9']`
> 而 `get()` 去读 `local['rl:m:u9']` —— 永远读不到，表现为「限流永远放行」。

### 13.5 fail-open 的落点

| 情况 | 行为 |
|---|---|
| Redis 可用 | 权威计数判定；主路径 |
| Redis 命令失败 | 放行 + 累加 `degradedPassCount` + 首次触发告警；**保留同实例本地兜底计数** |
| 降级次数 ≥ 100 | `shouldAlertDegrade()` 为真 → 说明 Redis 真挂了，不是瞬时抖动 |

保留本地兜底的理由：Redis 挂掉的瞬间，单实例上的高频攻击仍被挡住，
跨实例的绕过我们接受（毕竟已告警）。这比「完全放行」好，也比「fail-closed 全拒」好——
后者在 Redis 重启的 5 秒里会把全部正常用户拒掉。

## 14. 云函数中转（`cloudfunctions/judgeSubmit`）

### 14.1 为什么前端不能直连判题服务

1. **前端无法安全持有 token**。小程序包可被反编译，写进代码的密钥等于公开。
   一旦泄漏，攻击者能直接对判题集群发起无限提交——这是最容易被打的成本攻击面。
2. **身份必须由服务端确定**。前端传的 `userId` 不可信：改一个人的提交量
   就能把别人的限流额度用光（甚至让人被封）。所以 `userId` 一律取
   `cloud.getWXContext().OPENID`，并**忽略请求体里的任何 userId 字段**。

### 14.2 职责只有三件

1. 取当前用户 openid（唯一可信身份来源）
2. 按鉴权协议构造请求并转发
3. 把判题服务的错误归一化成前端可直接用的结构

### 14.3 字段白名单（不是黑名单）

```js
const ALLOWED_REQUEST_FIELDS = ['submissionId', 'questionId', 'type', 'language', 'code', 'limits'];
```

白名单而非黑名单的理由：判题服务只认识这几个字段，多传的东西要么被忽略、
要么成为攻击面（例如有人塞 `userId` 试图覆盖身份）。
另一个好处是**契约加字段时会立刻发现「这里没同步」**。

### 14.4 两层错误对象不能混用（踩过的坑）

| 概念 | 形态 | 用途 |
|---|---|---|
| 裸错误对象 | `{ code, message, retryAfterMs? }` | `sanitizeError()` 的产出，仅用于组装 |
| 最终返回结构 | `{ ok: false, error: <裸错误对象> }` | 直接 return 给调用方 |

混用的结果是 `{ error: { ok:false, error: {...} } }` —— 前端读 `result.error.code` 是
`undefined`，只能显示兜底文案。**这类 bug 不抛异常、不进日志，只是把提示语变模糊**，
所以自检里对它做了逐字段断言。

### 14.5 鉴权协议的三份实现怎么保证不漂移

| 位置 | 语言 | 为什么不能共享 |
|---|---|---|
| `judge-service/src/auth/hmac.ts` | TS | 服务端 |
| `cloudfunctions/judgeSubmit/index.js` | 纯 JS (CJS) | 云函数不走类型剥离，写 TS 语法直接启动失败 |
| 本文档 | 文档 | 人读 |

保证方式：自检用**同一组测试向量**分别调两边的 `canonicalString()`，断言逐字节相同；
再用云函数产出的请求头去调服务端的 `verify()`，跑通完整验签链路。

> 这是刻意的取舍。共享模块需要打包流程，而「打包流程本身出 bug」比
> 「两处实现漂移」更难发现。

### 14.6 云函数环境变量

| 变量 | 说明 |
|---|---|
| `JUDGE_ENDPOINT` | 判题服务**内网**地址。绝不要配公网域名 |
| `JUDGE_INTERNAL_TOKEN` | 与判题服务一致（两边必须同时轮换） |
| `JUDGE_FORWARD_TIMEOUT_MS` | 转发超时，默认 15000。**必须小于云函数超时（config.json 里 20s）** |

## 15. 题库来源适配层（外部依赖入口）

### 15.1 为什么要有这一层

判题服务需要「某道题在某语言下的测试点」（`JudgePlan`）。这些数据最终住在
云开发数据库里（题库后台录入 + 人工审核 + 版权台账），但云服务还没搭。

做法是把这条链路拆成三段，云服务搭好后**只换中间一段，主流程一行不动**：

```
PlanSource          →   PlanRepository        →   PlanProvider（内核只认这个）
内存 / HTTP / 云开发     规范化 + 缓存 + 错误语义       judges/index.ts
```

| 文件 | 职责 |
|---|---|
| `src/questions/source.ts` | 端口 `PlanSource` + 三个实现 + `normalizeJudgePlan` 规范化 |
| `src/questions/providers.ts` | `PlanRepository`：缓存、错误区分、规范化接线 |
| `src/judges/index.ts` | 主流程。**不 import 任何具体题库实现**（自检会拦） |

### 15.2 三条不能破的纪律

**① 绝不把网络错误说成「题目不存在」**

两者对用户的含义完全相反：

| 实际原因 | 应该给用户看 | 用户会做什么 |
|---|---|---|
| 题库说没有这道题 | 题目不存在或未配置判题计划 | 去反馈「这题是不是下架了」 |
| 题库接口抖了 | 题库暂时不可用，请稍后重试 | 重试 |

混在一起 → 用户对着「题目不存在」反复重试，**白等**。
所以 `PlanSource` 用 `{ ok, value?, error?, retryable? }`，而不是 `T | undefined`；
`PlanRepository` 把「查不到」抛成错，主流程 `catch` 后给 5xx 语义。

**② 成功才缓存；失败与「确实没有」都不缓存**

判题是高 QPS 路径，每题打一次题库会把题库拖垮。但：

- 缓存**失败** → 一个瞬时抖动被固化成「这题永远坏了」，得等 TTL 才恢复
- 缓存**空结果** → 题库存在「先建题后录测试点」的窗口期，运营刚录好、用户还得再等一个 TTL

**③ 规范化不是可选项**

题库是人工录入的，脏数据一定出现，而脏数据会一路突破到测试点比对，
表现为「用户答案全对但判错」——最贵的那种 bug。

原则是**能修的修、不能修的拒**（不是不合格就整条扔掉，扔掉等于用户答了好题却拿不到分）：

| 情况 | 处理 | 为什么 |
|---|---|---|
| 缺 `index` | 按顺序补 | 顺序信息本来就在数组里 |
| 数字型 `expected`（`15`） | 转字符串 | 题库里很常见 |
| `\r\n` 行尾 | 归一为 `\n` | Windows 上录题会带进来，逐行比对永远不等 |
| 未知 `compare` | 退回 `exact-lines` | 有合理默认 |
| 期望输出超长 | **拒** | 截断会让「输出正确的用户」判错，比报错更坏 |
| 测试点超过 50 个 | 截断 + 记 fixes | 防题库被写坏导致一次提交跑上千个容器 |
| 无测试点 / 语言不支持 / 配额非法 | 拒 | 无法修复 |

### 15.3 三个通道与配置

| `JUDGE_PLAN_SOURCE` | 用途 | 需要的配置 |
|---|---|---|
| `memory`（默认） | 开发与自检。只能判内置样例题 | —— |
| `http` | 自建题库后台（与判题服务同网段） | `JUDGE_PLAN_BASE_URL`、`JUDGE_PLAN_TOKEN` |
| `cloud` | 云开发 HTTP 访问服务 / 云函数 HTTP 触发器 | 上面两项 + `JUDGE_CLOUD_ENV_ID` |

**为什么不引 `@cloudbase/node-sdk`**：判题服务是唯一主动执行陌生人代码的组件，
依赖越少攻击面越小（与 `redis/client.ts` 自建最小客户端同一决策）。
云开发的 HTTP 访问服务本身就提供 HTTPS 入口，用内置 `fetch` 走它就够。

接口形状：

```
GET {baseUrl}/plans/{questionId}/{language}
Authorization: Bearer {token}
→ 200 { ...JudgePlan }       或  { plan: {...} } / { data: {...} }
→ 404                        （明确答复：这道题没有判题计划）
→ 401/403                    （凭据错，不可重试）
→ 5xx                        （可重试）
```

**云函数侧等真正搭云服务时必须做两件事**：
1. 校验调用方身份，不能裸奔（判题服务带 Bearer token，云函数侧要验）
2. 只读 `judge_plans` 集合，不要复用一个通用查询函数

### 15.4 已知边界

- 请求超时 3s（`JUDGE_PLAN_TIMEOUT_MS`），测试点缓存 5 分钟（`JUDGE_PLAN_CACHE_TTL_MS`）
- 缓存是**每个实例各自一份**，运营改测试点后需要等 TTL，或调 `PlanRepository.invalidate()`
- 目前没有「题库主动推送变更」的通道。冷启动阶段用 TTL 足够；如果以后要秒级生效，
  加一个带签名的 `POST /internal/invalidate` 即可，不用改主流程

## 16. 结果缓存 Redis 化（幂等的生产实现）

`src/redis/result-cache.ts`，替换 `adapters.ts` 的 `MemoryResultCache`。

**幂等不是性能优化，是正确性要求**：同一份提交被判两次，可能一次 SE 一次 AC，
用户看到的结果会自相矛盾。内存实现下「落在哪个实例」决定能不能命中。

### 16.1 三处降级方向（最容易顺手抄错的地方）

| 组件 | 降级方向 | 代价 |
|---|---|---|
| 限流计数 | **fail-open**（放行） | 多烧算力（可恢复） |
| 结果缓存 | **fail-open**（不缓存，重跑） | 多烧算力（可恢复） |
| 重放拦截 | **fail-degraded**（退回单实例内存） | 少挡重放（安全事件） |

前两者同族、第三者相反。代码里用 `DEGRADE_POLICY` 常量把结论钉住，自检会断言三者不全相同。

### 16.2 三个实现细节

**① 读回的值当不可信输入校验**

Redis 里的值可能来自旧版本代码、可能被手工改过、可能被截断。
`parseResponse()` 做形状校验（必需字段齐不齐），不像就当作未命中。
代价是少命中一次，收益是不会把脏数据当结果发给用户。

**② `system-error` 不缓存**

那是设施故障。缓存下来等于让用户永远看到同一个错误，即使故障已恢复。
与内核的「错误结果也缓存」不冲突——内核缓存的是**用户代码导致的**错误
（同一份错代码重提应该得到同一结论），这里过滤的是**设施导致的**错误。

**③ `localOnly` 标记**（真实踩到的坑）

超大结果（超过 `maxValueBytes`）只写本地、不写 Redis。但 `get()` 的原则是
「Redis 权威」—— Redis 返回 `null` 就判未命中。于是这些结果**写进去却永远读不到**，
本地那份纯属内存泄漏，且没有任何报错。

修法：这类项打 `localOnly: true`，让 `get()` 知道「Redis 里注定没有，去本地找」。
反向也守住了：Redis 已删除的普通结果**不会**从本地兜底复活。

## 18. 本地判题模式（不装 docker、不买服务器）

> 面向非技术读者的说明见 `本机跑起来-保姆级说明.md`。
> 本节只记工程约定与验收口径。

### 18.1 为什么要有这个模式

判题服务最贵的一环是「跑代码」。但项目在最早期（自己开发、自己录题、内容还没上线）
**不该为此付服务器钱，也不该为此先装一整套 docker**。

有了 `JUDGE_SANDBOX=local`，**零成本就能验证整条链路是通的**：
提交 → 编译 → 逐测试点运行 → 比对 → 出结论。

### 18.2 两种后端，同一个接口

| | `DockerExecutor`（生产） | `LocalExecutor`（开发） |
|---|---|---|
| 隔离 | 12 项全开 | **零隔离** |
| 内存上限 | cgroup | 无（MLE 判不出来） |
| 进程数上限 | pids.max | 无（防不住 fork 炸弹） |
| 网络 | `--network none` | 无（能联网） |
| 文件系统 | 只读根 + tmpfs | 无（可写本机） |
| 用途 | 上线、有别人提交代码 | 自己开发 / 录题验证 |

两者实现同一个 `Executor` 接口，**编排层对后端无感知**。
`SandboxPlan` 由同一个纯函数产出——本地模式做的是**路径翻译**
（容器路径 `/box`、`/box-artifact` → 宿主路径），
**不是第二套语言配置**，避免「两套配置漂移」。

### 18.3 三条硬约束（都有自检锁死）

**① 默认值必须是 `docker`。** 安全选项才配当默认值。
未知取值告警后按 `docker` 处理，不会静默跑在不安全模式。

**② 生产 + local = 直接拒绝启动**（`loadConfig()` 抛错）。
这是唯一的安全闸门，不给「先上线再说」的机会。

**③ 启动必须打醒目告警**，列出失效的防护（内存/进程数/网络/只读 fs）。
**不知道边界的降级，比明确的降级危险得多。**

### 18.4 本轮修出的 5 个真 bug（只有真跑才暴露）

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | **stdin 从来不传** | 读输入的程序全卡住 → **误判 TLE**，学生会去优化算法 | `SandboxPlan.stdin` + 两个执行器喂完**立刻 end()** |
| 2 | Python 产物收集无条件调用 | 解释型语言无产物 → 报「产物未生成」 | 与 `needsArtifactMount` **同源**判断 |
| 3 | 本地找不到 gcc | 「装了却报没有」，用户反复重装 | `resolveExecutable()` 自己解析绝对路径 |
| 4 | 编译产物目录没建 | `ld: cannot open output file: No such file` | 执行器**执行前预建**（docker 时间线是编译后才建） |
| 5 | 产物目录推导依赖挂载 | 编译阶段按设计无该挂载 → **重定向永远不生效** | 两级回退：挂载 → workDir 同级 `.artifacts` |

> **第 1 条为什么自检抓不到**：自检用的假执行器不读 stdin，
> 所以永远不会发现「漏传输入」。这是「假执行器测不出来、只有真跑才暴露」的典型。

### 18.5 Windows 特有的三个路径坑

1. **拆 `host:container` 不能用「从右往左找冒号」**——Windows 盘符也是冒号。
   `D:/ws/sub:/box` 会被拆成 host=`D`、container=`/ws/sub:/box`。
   正确判据：**容器路径必以 `/` 开头**，找「冒号+斜杠」的位置。
2. **路径嵌在参数内部**（Python 的 `-c 'py_compile.compile("/box/main.py")'`）
   需要额外的**带边界断言的文本替换**，只做整参数替换会漏
   → 表现为「Python 编译总是失败」而用户代码没问题。
3. **统一正斜杠**：反斜杠嵌进 Python 字符串会触发
   `SyntaxError: 'unicodeescape' codec can't decode bytes`（`C:/Users` 里的 `\U` 被当转义符）。
   例外：UNC 路径 `//server/share` 的开头双斜杠**有语义**，要保留。

### 18.6 本机验收口径

```bash
node judge-service/scripts/local-smoke.mjs
```

期望输出（C/C++ + Python，覆盖四种结论）：

```
通过  正确答案 → 应判 AC        → accepted（通过 3/3 个测试点）
通过  用 int 会溢出 → 应判 WA   → wrong-answer（通过 2/3 个测试点）
通过  语法错误 → 应判 CE        → compile-error
通过  数组越界崩溃 → 应判 RE    → runtime-error
通过  Python 正确答案 → 应判 AC → accepted（通过 2/2 个测试点）
通过 5 项，失败 0 项，跳过 0 项
```

第 2 项特意用 `int` 存累加和（`1..100000` 的和 5×10⁹ 超 int 上限）：
小数据过、大数据溢出 → 被判 `2/3`，**恰好证明隐藏测试点在起作用**。

### 18.7 本地模式自检覆盖（判题服务自检第 18 节，53 项）

- 卷参数拆分（盘符冒号、POSIX 路径、host 侧含 `:/`、反斜杠、非法输入）
- 路径统一（折叠重复斜杠、反斜杠转正斜杠、**UNC 开头双斜杠保留**）
- 挂载映射（长路径优先，`/box-artifact` 不被 `/box` 截胡）
- 参数内文本替换（命中 Python 代码串 / **不做无边界替换**）
- 包装脚本解析（只取第一条命令、正确处理 `'\''` 转义）
- 产物重定向（编译阶段改 `-o`、运行阶段兜底、不改原数组、统一正斜杠）
- 产物目录（自己推导、执行前预建、后缀取自常量不写死）
- 命令解析（解析成绝对路径、同时读 `Path` 与 `PATH`、补 `.exe`、失败不拒执行）
- stdin 链路（编译阶段 `undefined` / 运行阶段**空串也要显式给**）
- 安全底线（**跑行为断言**：生产+local 必须抛错、开发+local 正常、告警存在、默认值是 docker）
